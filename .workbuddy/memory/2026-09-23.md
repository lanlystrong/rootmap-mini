## 数据接入后端内容下发接口
- 现象：小程序词/词根/词缀数据此前全部来自本地 `data/index.js` 打包内置，`api.js` 只有登录/事件/统计接口，未走后端内容接口（用户反馈"数据没有查询后端接口"）。
- 服务端 `server/src/contentRouter.js` 已挂载 `/api/content`（免鉴权），且 `server/src/content.js` 直接 `require('../../miniprogram/data/index')` —— 与小程序打包内容同源同构。
- 改造：
  - `utils/api.js` 新增 `contentMeta()`(GET /api/content/meta) 与 `fetchContent()`(并行 GET /roots·/affixes·/words)。
  - `utils/content.js` 数据来源改为「本地缓存(后端同步) > 打包内置(兜底)」，`getContent()` 同步签名不变；新增 `syncFromServer()`（checksum 增量比对，未变跳过整包拉取，落本地 `rm_content_v1`，失败静默回退）与 `setContentRaw()`。
  - `app.js` 启动 `syncContent()` 冷启动异步拉取（不阻塞、不依赖登录）；`pruneStaleCards` 改用 `getContent()` 当前生效交付集做下架清理。
- 验证：node 单测覆盖 打包内置→后端同步→本地缓存→checksum 跳过→离线回退 全链路 PASS。
- 注意：`api.js` 的 `BASE='http://127.0.0.1:3000'` 仍为硬编码（清单第1项），真机需改 LAN IP 或合法域名。

## 词根关联单词数落库（rootmap-server）
- 现状：`roots` 表此前无 `word_count` 字段，`seedContent` 写 roots 时(roots 先于 words)无从算关联数，故从未落库；关联数权威来源是 `words.root_id`(由 breakdown 的 root 段 refId 写入)。
- 改动：
  - `db.js` CONTENT_DDL 的 roots 表加 `word_count INT NOT NULL DEFAULT 0`；`migrateContentColumns` 的 want 数组补 `['roots','word_count','INT NOT NULL DEFAULT 0']`(旧库启动补列)。
  - `seedContent.js`：words 全部落库、commit 前用 `UPDATE roots r LEFT JOIN (SELECT root_id,COUNT(*) c FROM words WHERE root_id IS NOT NULL GROUP BY root_id) g ON g.root_id=r.id SET r.word_count=COALESCE(g.c,0)` 回填(未来导入自动生效)。
  - `contentStore.js` `readDataset` 的 roots 构造加 `wordCount: r.word_count || 0`(经 `/api/content/roots` 自动下发,指纹/diff 字段集未动,安全)。
  - 新增 `scripts/backfill-root-wordcount.js`(幂等:补列+聚合回填+一致性校验+TOP5抽样),`package.json` 加 `backfill:rootcount`。
- 已执行：`npm run backfill:rootcount` 对 rootmap_1 写库成功 —— 213 词根全部更新(影响 213 行),Σword_count=1350 == root_id 非空单词数 1350,一致通过。TOP5: stan47/vis29/fer28/fac28/pos24。
- 注意：脚本一致性校验初版因 `SUM()返回字符串 vs COUNT()返回数字` 用 `===` 误报,已改为 `Number()` 归一。

## 小程序数据只来源后端、不落本地存储（content.js 重构，取代上一条本地缓存方案）
- 用户要求：小程序数据只来源于后端接口，**不**在本地存储（移除此前 `wx.storage(rm_content_v1)` 缓存与 `require('../data/index')` 打包内置兜底）。
- `utils/content.js` 重构：
  - 删除 `STORE_KEY`/`readStore`/`writeStore`/`loadRaw`/`setContentRaw`/`syncFromServer`，不再写任何 wx.storage、不再引用本地 data。
  - 内存单例 `cached` + `inflight`(进行中 Promise 去重)；`getContent()` 同步返回(冷启动/离线为 null)；新增 `ensureContent()`(异步:内存有则直接返,否则 `api.fetchContent()` 并行拉 roots/affixes/words 填内存,失败返回 null)、`isLoaded()`。
  - 会话内只拉一次(内存复用),无任何本地数据来源。
- `app.js`：`onLaunch` 调 `preloadContent()`(ensureContent 预载),加载完成后再 `pruneStaleCards`；`pruneStaleCards` 加 `!data` 空值保护(离线不误删进度);保留 `syncContent` 别名兼容。
- 6 个页面渲染入口加 guard：未 `isLoaded()` 则 `ensureContent().then(()=>{ if(isLoaded()) this.onShow/onLoad(opts); })`，失败保持空态、**不**递归重试(避免离线死循环)；`home/review/profile` 的 `onLoad` 移除陈旧 `this._c=getContent()`，改 `onShow` 设 `this._c`。
- 验证：8 个 JS `node --check` 通过；node 自测 PASS —— 后端拉取→words=1350、缓存命中同引用、并发去重(仅 3 次请求)、离线返回 null/getContent=null/不崩、加载过程 setStorageSync 调用 0 次。
- 影响：离线或后端未就绪时小程序显示空态(无本地兜底)，属预期；真机必须配 request 合法域名或改 `api.BASE`(硬编码 127.0.0.1:3000 仍未解决,清单第1项)。

## 修复 NavBar 头部显示问题（components/NavBar + 6 页面）
- 现象：用户反馈"小程序头部显示有问题"。
- 根因：`index.wxss` 的 `.nb-bar` 用 `padding-top: statusBarH` 撑状态栏，而内部返回键 `.nb-back`/标题 `.nb-title-wrap` 用 `position:absolute; top:0; bottom:0` —— 绝对定位相对**包含块 padding box**，使 `top:0` 落在 `padding-top` 状态栏区域内，导致返回箭头与标题**压到手机系统状态栏（时间/信号/电池）上重叠**；且标题 `right:120rpx`(≈60px) < 右侧胶囊宽(≈87px)，长标题与胶囊重叠。
- 修复：
  - `index.wxml`：新增独立 `.nb-status`(透明,占位状态栏高) + `.nb-inner`(height:navH, `position:relative` 作为返回键/标题的包含块)，`.nb-bar` 直接 `height:totalH` 不再用 padding-top。
  - `index.wxss`：返回键/标题改相对 `.nb-inner`（仅落在状态栏下方，不再侵入状态栏）；标题 `right` 由 120rpx 改 180rpx 避让胶囊。
  - 6 个页面 navbar 统一移到页面根容器**外**（home/index/review/profile 原在带 padding 的 `.xx-page` 容器内，现与 root-detail/word 一致放最外层），结构彻底统一，并规避祖先容器 future transform 影响 fixed 栏的风险。
- 验证：6 个页面 navbar 均位于 wxml 第 1 行、页面根容器之外；组件标签闭合正确。开发者工具导入 `miniprogram/` 预览即可确认状态栏不再被遮挡。
